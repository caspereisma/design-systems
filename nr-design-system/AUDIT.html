How this page is used

This audit is a working document, not a report that gets read once. Casper reviews it, does the Figma and decision work it describes, and leaves comments on the page as he goes. Claude folds those comments back into the page in batches. The loop:

  1. Review and work. Read a section, do the work in Figma, Storybook or with the team.
  2. Comment where the change belongs. Anchor each comment on the exact text, swatch or table row it refers to; the anchor is what tells Claude the target. No need to mention Claude in the comment. Start every comment with one of the four prefixes below.
  3. End the sprint in chat. When a review sprint is done, say “review comments” in the Claude Code session. Claude reads every thread, makes the changes, republishes the page once at the same link, and reports in chat what changed and what it did not do and why.
  4. Close the threads. Casper sends the threads he wants closed to Claude (reply with Send to Claude or mention @claude). Claude replies in each with what was done and resolves it. Threads not sent stay open for Casper to resolve by hand.

Comment prefixes

Two rules Claude follows

  • Comments are requests; chat is authority. Reversible edits to this page and its files happen from comments alone. Anything outward-facing or hard to undo — pushing to nr-ui-tools, opening a PR, deleting a Figma collection, touching staging — is confirmed in chat first, whatever a comment says.
  • Checklists are live. Decisions (3), Figma steps (4), the variable remap (4.1), tickets (5), Storybook practices (6) and deletions (8) all have shared ticks saved with the page. Tick as you complete; comment on a row for anything that needs a word.
  • The page is the log. Every DECISION and DONE lands in the Decision log at the bottom with a date, so the page records what was agreed and when, alongside the original findings.

Caveat: after a republish that changes the text a comment is anchored to, open threads can drift or detach. Resolve threads at the end of each sprint so this stays rare.

The one-paragraph verdict

You have three design systems that each believe they are the real one: the Figma library, the code that ships, and the prototype you design in. They agree on the boring parts (font, corner radius, spacing unit, white background) and disagree on every part anyone ever customised: all six semantic colours, two heading sizes, a heading weight, and the status chip. Nobody noticed because the disagreements are between near-identical greys and oranges. That is not reassuring; it is the exact condition under which drift compounds.

Why this happened — the one mechanism to understand

The Figma library is the official Material UI kit with FUGA colours added beside the Material ones. Both palettes ended up in the file: material/colors (spelled grey/800) and fuga/colors (spelled Grey/800). Whoever customised the kit re-typed the hover, focus and border tokens with FUGA values by hand, but left the main colour tokens pointing at the Material palette — almost certainly because the two grey/800s are indistinguishable in a picker.

error/main→ aliasesmaterial/colors · red/500#F44336
error/_states/outlinedBorder= typedFUGA Red 500 at 50 %#F44139
primary/main→ aliasesmaterial/colors · grey/800#424242
primary/_states/hover= typedFUGA Grey 800 at 4 %#404041
Inside your own file, a button’s fill and its border come from different brands. The library disagrees with itself before code even enters the picture.

Everything in this audit follows from that one miswired alias. Fix it and most of the colour drift collapses.

Text is solid, not alpha. Decided 11 Sep: text/primary grey/900, text/secondary grey/700, text/disabled grey/500, replacing Material’s 87 / 60 / 38 % black. Same look on white, but a fixed colour means contrast is computed once, rendering stays crisp, and Figma equals browser. The rule behind it, agreed alongside:

RoleSolid or alphaWhy
Text, fills, chip backgrounds, brand, alertsSolidOne hex, one rendering. Contrast fixed once. Exports everywhere.
Component borders (chip, input)Solid tintThe surface beneath is fixed, so alpha buys nothing. red/200 ≈ red/500 at 50 % on white anyway.
Hover, selected, focus, pressed, disabledAlphaSit on many surfaces; one token must read right on all of them. Now {role}/main + state-opacity/* (Figma alias-with-opacity, since 3 Sep 2026).
Backdrop, scrim, skeletonAlphaOverlays by nature.
DividersSolid grey/300Alpha only where they cross tinted rows.

Three guards: alpha never for text; never stack two alpha layers; every alpha state checked on the darkest surface it can sit on.

3.3 Dark mode: kept for the future decided

Decided 11 Sep: dark mode stays. It is a future capability, not a current build item, so the Figma palette keeps its Dark mode and every token stays two-mode. What that means in practice:

  • The Dark column in 4.1 applies. state-opacity keeps its dark values (hover 8, selected 16), the Material dark paper-elevation greys stay (d04).
  • Ticket 3’s tokens.json carries a dark set from day one. It costs almost nothing, since Figma already has the values, and it stops dark mode becoming a second migration later.
  • Shipping dark mode in the product is still a Brief when its time comes. Nothing in code renders it today.

What you can fix yourself, in Figma, this week

All inside NR MUI v6.1. None of it needs engineering. Publishing the library afterwards updates every screen that uses it.

Steps done: 0 / 7

  1. Re-point the six main tokens (primary, secondary, error, warning, info, success, plus their dark and light variants) from material/colors to the matching fuga/colors ramp, in both Light and Dark modes. Use the values from 3.1.
  2. Re-alias the _states tokens to {role}/main with their own opacity (hover 4 %, selected 8 %, focus 12 %, focusVisible 30 %, outlinedBorder 50 %). Figma supports alias + opacity since the 3 September 2026 release “Control opacity at scale”, and the opacity can be a number variable, so put the five percentages in one small set scoped for colour variables. Both modes then follow the mains automatically; the Dark-mode Material literals disappear with them.
  3. Bind the Status chip backgrounds. On all 25 variants the background is a typed hex. Bind each to the matching {role}/light or a new {role}/_states/background token. Add a Purple colour variant for Relinquished. open Purple variant exists but copies Grey; backgrounds still literal on all six.
  4. Rename the FUGA ramps to match the Material convention (Grey/800 → grey/800, Fuga-Blue → fugaBlue, naxos-blue → naxosBlue, Base/White → common/white). Consistent casing is what stops the wrong alias being picked next time. done Lowercase ramps, base/White; fuga-Blue and fuga-Green kept a capital. naxos-blue removed.
  5. Delete material/colors once nothing aliases it. 252 variables that exist only to be picked by mistake.
  6. Tidy the small things: fix the typo knowFillDisabled → knobFillDisabled; set breakpoints/xs to 0 (MUI’s default; 444 is a frame width); rename _fontSize/0,625rem style names to use a dot. partly knobFillDisabled renamed. breakpoints/xs still 444; nine _fontSize names still use a comma.
  7. Scope the variables. Most are ALL_SCOPES, so every colour appears in every picker. The kit’s own text/* tokens show the pattern: text colours scoped to text fill, surface colours to frame fill, border colours to stroke. This is the single biggest quality-of-life improvement for anyone designing in the file. open 61 palette tokens still ALL_SCOPES. state-opacity/* already COLOR_OPACITY.

Storybook as your tool

Today Storybook is engineering’s test harness that happens to be viewable. It can be your living spec. What that takes:

Done: 0 / 6

  • Foundations pages you author. Colour roles with usage rules, type scale with do/don’t, spacing, elevation, and the status vocabulary from 3.2. Storybook supports prose pages (MDX). There are none today. This is designer-owned content.
  • A token page that cannot lie. Today’s “Design System / Tokens” page renders the 12 raw paint ramps and hardcodes its own swatch colours. It should render from tokens.json (Ticket 3), organised by role, so it is always true.
  • Stories as designed states. Each story is one state you designed: default, hover, error, loading, empty. Today the 474 stories prove components mount. None test an interaction. Every dialog and dropdown should have at least one story that clicks through the flow; this is where “does the design work” gets checked automatically.
  • Accessibility as a gate, not a panel. The accessibility checker is installed and set to “show but never fail”. Once the current violations are listed, flip it to fail the build. Contrast problems then get caught the day they are introduced.
  • A “Figma MUI design library” section. One page per Figma component set: the MUI component under the production theme in the variant × state × size matrix the Figma set defines (hover, focus, pressed forced), a Design tab embedding the live Figma set (@storybook/addon-designs), and a Design Tokens tab plus doc-page tables listing the variables the set binds (storybook-design-token, reading the generated tokens.css). Pilot of 3 pages (Button, Chip, Status) on design-system; 29 to go.
  • Chromatic as design review. Already live on the design-system branch. Every push produces a visual diff of all 474 stories against the baseline. You approve or reject changes in a browser. This is the mechanism that makes the colour migration safe: when the six mains change, you see every affected component at once.

Glossary

Token
A named design decision (primary/main) rather than a raw value (#404041). Change the token, everything using it changes.
Primitive
A raw colour in a ramp (Grey/800). Never used directly by a component.
Semantic role
A token that names purpose (error/main, text/secondary) and points at a primitive. Components use these.
Alias
A token that points at another token instead of holding a value. primary/main → Grey/800.
Variable (Figma)
Figma’s implementation of a token. Lives in a collection, can have modes (Light/Dark).
Style (Figma)
The older mechanism; text and effect styles are still styles here, colours are variables.
Story (Storybook)
One rendered state of one component. Storybook is the catalogue of all of them.
Chromatic
A service that screenshots every story on every push and shows you what changed.
Semantic layer
The middle tier of tokens (roles). Figma has one; code does not.

Provenance. Figma read via the Plugin API: every local variable collection, values resolved through aliases; the Status component’s 25 variants read for fills, strokes and bound variables. Code scanned at nr-ui-tools staging @ edd73c2; Storybook counts from a live build (130 docs pages, 474 stories).

Known limits. Component-variant coverage was sampled (Status only); the other NR MUI v6.1 component sets were not diffed against code props. DMP/colors consumers were not traced.
